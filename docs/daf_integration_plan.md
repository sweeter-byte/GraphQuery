# 🚀 DAF 真实下游引擎集成方案 (GraphQuery - Fastest)

## 📌 方案背景

目前 `Fastest-par` 的核心能力在于**基数估计（Cardinality Estimation）**与**最优匹配序列探索**，可以为下游真实的图数据库/查询引擎提供理论上最优的**查询匹配顺序（Matching Order）**。
为了使得系统闭环，让用户能在前端提交查询图并在真实数据上获得精确的匹配结果（如返回实例总数及实际运行时间），我们需要集成一个真实的图查询后端。

经过严谨的技术调研与方案比对，最终选定 **DAF (SIGMOD 2019)** 作为下游的真实子图匹配引擎。此方案具备极高的学术与工程验证价值，能够直观地通过实验证明 **"更优的排列顺序能够显著提升顶流 Matching Engine 的性能"**。

---

## 🏗️ 核心实施路线

具体的工程改造分为三个关键步骤。

### 步骤 1：引入及精简开源代码 (Codebase Integration)
将 `SNUCSE-CTA/DAF`（或 `bookug/siep` 中的 DAF 模块）的 C++ 源码作为 submodule 或第三方库直接引入到目前的 `Fastest-par` 目录结构中（例如放置在 `engines/daf/` 目录下）。
- 修改 DAF 原有的 Makefile / CMakeLists，使其能够单独编译出一个可通过命令行调用的可执行文件。
- 精简掉与核心匹配算法无关的多余代码（例如其他对比算法的基准代码）。

### 步骤 2：深度魔改"匹配顺序生成"逻辑 (Order Injection)
DAF 原本会基于自己的代价模型和启发式规则来动态生成一个匹配顺序。这是本方案的技术难点与重点。
- 深入阅读并分析 `GenerateMatchingOrder`（或相应的函数）在 DAF 源码中的逻辑。
- 切断并**覆盖**其原生的启发式排序代码逻辑。
- 增加外部输入接口（无论是通过命令行参数传递整数数组如 `0,2,3,1`，还是通过特定的`.order`文件读取），强制让引擎的递归搜索树按照 **Fastest 推荐的最优拓扑序列**展开。

### 步骤 3：数据与接口桥接 (FastAPI - C++ Adapter)
在 Python 后端的 FastAPI (`server/routes/sessions.py -> execute_query`) 中完成整个流程的串联：
1. **数据准备**：将用户在前端画板上构造的最新查询图结构，转换为 DAF 支持的纯文本格式（`t`, `v`, `e`格式），并保存到本地临时文件（如 `/tmp/query.graph`）。
2. **提取序列**：从当前 session 的排行榜中提取得分最高的最优节点排列顺序数组。
3. **系统调用**：通过 Python 原生的 `subprocess.run` 等方式，调用魔改后的 DAF 可执行文件。
   ```bash
   # 预期调用的示例命令:
   ./engines/daf/build/DAF_executor -d <data_graph> -q <query_graph> -o 0,2,3,1
   ```
4. **结果捕获与返回**：捕获 C++ 程序的标准输出 stdout，解析出最终的**匹配总数**和**真实执行耗时**，打包成 JSON 格式通过 HTTP 返回给前端 `EvaluationDashboard` 组件展示。

## 🎯 预期业务价值与成效

完成此方案后，GraphQuery 系统将具备以下全新能力：
- 用户可以点击前端右下角的【执行下游引擎】。
- 右侧面板或弹窗内将真实展示：使用当前最优排列，在诸如 DAF 这种 SOTA 引擎上，查出了多少万个子图，共耗时多少毫秒。
- 极具学术说服力，直接验证 **"FaSTest 基数估计优化出的执行计划，可以让顶会匹配器如虎添翼"**。
