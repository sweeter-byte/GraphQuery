# 混合并发架构优化策略：Python 线程池 vs C++ OpenMP

## 1. 当前架构的性能瓶颈：线程超额订阅（Thread Oversubscription）

在目前的 Fastest-par 系统中，因为我们移除了 C++ Pybind 层的全局锁并在 Python 层使用了 `asyncio.gather` 并发提交任务，系统现在呈现出**双级混合调度**状态：

*   **第一级 (Python 层)**：`session_pipeline.py` 会将同一 Level 的所有候选前缀图（例如 $K=10$ 个不同的 Order）同时抛入 Python 的线程池（默认由操作系统核心数 $N$ 决定，或更高）。
*   **第二级 (C++ 层)**：在 `CandidateGraphSampling` 阶段，如果采样候选集较大，`#pragma omp parallel num_threads(GraphLib::num_threads)` 会为**每一个前缀**内部再次启动最多 $N$ 个 OpenMP 工作线程。

**后果：** 
如果一台机器有 16 个物理核心（$N=16$），在最坏情况下，会同时激活 $K \times N = 10 \times 16 = 160$ 个重负载计算线程抢占 16 个物理核心。
这会导致极度频繁的**上下文切换 (Context Switching)** 和 **CPU 缓存失效 (Cache Thrashing)**，反而大幅降低吞吐量，阻碍基数估计的真实性能。

---

## 2. 三种可行的调整方案

为了让引擎在多核下发挥出最大的运算效率，这里提出三种不同的线程分配策略供您评估：

### 方案 A：粗粒度并发（前缀级并发，禁用内部 OpenMP）
以"个前缀图"为最小并行执行单元，让 Python 层接管所有的多核调度，C++ 层专注串行计算。

*   **配置**：
    *   Python 线程池最大工作线程数 (max_workers) = $N$
    *   C++ `set_option(num_threads=1)` 强制禁用 OpenMP
*   **优点**：
    *   **零竞争**：系统总线程数恒定为 $N$，每个核心被一个前缀图独占，CPU Cache 命中率极高（因为没有线程争抢数据）。
    *   避免了 OpenMP 的 Fork-Join 线程管理开销。
*   **缺点**：
    *   如果遇到极个别超大的、极其难算的前缀图，它只能使用 1 个核心。也就是会出现"长尾效应"（其中 $N-1$ 个核心早早做完在此等待，剩下的 1 个核心孤军奋战）。
*   **适用场景**：图数据候选空间分布相对均匀、需要同时评估海量不同前缀的场景。

### 方案 B：细粒度并发（禁用 Python 并发，全权交给 OpenMP）
退回 Python 的串行循环，将并发的控制权全部交给底层的 C++ 逻辑去发掘候选点层的并行潜力。

*   **配置**：
    *   关闭 `session_pipeline.py` 中的 `asyncio.gather`，改回顺序 `await` 逐个请求。
    *   C++ `set_option(num_threads=N)` 开启全核 OpenMP 并发。
*   **优点**：
    *   遇到极难估算的超级大前缀图时，性能极佳，全核心协同合作。
*   **缺点**：
    *   如果前缀图非常小，或者局部图匹配很容易算完（候选集小），由于 OpenMP 自身有调度开销或者是触发了 `#pragma omp if (num_root_samples > ...)` 的禁用条件（回退为单线程），会导致多核利用率严重不足（比如只用了 1 核心，其余核心全在闲置挂机）。
*   **适用场景**：用户每次只关注 1 个前缀查询；或者每个前缀都极为吃算力。

### 方案 C：混合微调调度模式（折中兼容配置）
依然保留双层并发，但对总的线程预算进行严格人为按比例均分，比如将资源按 5:5 劈开。

*   **配置**：
    *   设定 Python 线程池的并发槽位上限限制为 $P$（例如 $P=4$ 或 $P=(N/4)$）。
    *   设定 C++ 的 `num_threads` $= T$（例如 $T=(N/P)$）。
    *   保证 $P \times T \approx N$，系统总运算线程尽量不多于机器物理核心。
*   **优点**：
    *   兼顾了宏观并行（同时跑 4 个前缀）和 微观加速（每个前缀有 4 核心合力帮忙）。
*   **缺点**：
    *   这个比例参数 $(P, T)$ 需要仔细的 Profile 测试，很难有一个"普适"最优解。

## 3. 最终建议：如何选择？

因为 Fastest-par 的基数估计算法是基于**独立采样（Sampling）**的轻量且快速的过程，**推荐采用方案 A**。

**为什么选方案 A？**
在多阶段搜索（Beam Search）和生成查询计划树的过程中，我们面对的是大量需要验证的短平快的小 Query（前缀）。基于此：
1. **数据相互独立性**：前缀 A 和前缀 B 之间的计算没有任何联系。宏观的数据隔离往往比微观在同一个任务上拆分线程的性能损失更小。
2. **长尾影响可控**：因为估计过程中设置了采样上限（如 $ub\_initial$ 和 Stratified Sampling），单个极大前缀的计算时间在实际中也会被强制阻断并限制采样深度，长尾效应因此被缩小了。

**如果您决定采用方案A：**
我们可以很简单地：
1. 定制一下 `session_pipeline.py` 的执行器 `loop.set_default_executor(ThreadPoolExecutor(max_workers=os.cpu_count()))`
2. 把 `estimator_adapter.py` 里面的 `num_threads=1` 写死。
